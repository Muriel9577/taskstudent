# Code review (етап 7)

Виконав AI-агент (Claude Sonnet 5.5): прочитав усі 10 файлів у `app/` і 2 файли JavaScript
(~1000 рядків) та оцінив за критеріями із завдання. Рішення про те, що виправляти, ухвалює студент.

## Результат за критеріями

| Критерій | Оцінка | Що знайдено |
|---|---|---|
| Читабельність | Добре | Короткі функції, коментарі українською, імена зрозумілі. Дрібне: невикористаний імпорт `ValidationError` у `subjects.py` (виправлено). |
| Структура проєкту | Добре | Шари: маршрути (blueprint-и), `services.py` (логіка прогресу без Flask), `validation.py`, `db.py`. Недолік: функція `error()` живе в `auth.py`, а імпортується з інших модулів. |
| Дублювання | Є, прийнятне | Допоміжні функції `api`, `text`, `button` скопійовано в `app.js` і `subject.js`. Логіка часткового оновлення (`x if "x" in data else row["x"]`) повторюється в `subjects.py` і `tasks.py`. |
| Обробка помилок | Добре | Один обробник `ValidationError` на рівні застосунку, чіткі 400/401/404/409, некоректний JSON не дає 500. Недолік: UI показує «Помилка», якщо сервер не відповів зовсім. |
| Безпека | Добре, з 2 знахідками | Хеші паролів, перевірка власника, 404 для чужого, `textContent`, ліміти. Знахідки: вхід хешував пароль будь-якої довжини; файл секретного ключа створювався з правами 644. Обидві виправлено. |
| Продуктивність | Прийнятно | Не було індексів на `subjects.user_id` і `tasks.subject_id` (виправлено). Сторінка предмета після кожної зміни перезавантажує всі три запити, для навчального обсягу це нормально. |
| Відповідність вимогам | Повна | Усі 5 функцій Хвилі 1 і 9 критеріїв з `project-context.md` покриті тестами. |

## Що виправлено в цьому етапі

| № | Знахідка | Виправлення | Тест (падав до виправлення) |
|---|---|---|---|
| 1 | `/api/login` не обмежував довжину пароля й e-mail: пароль до 1 МБ хешувався при кожній спробі (обхід обмеження 128 символів, яке було тільки в реєстрації) | Надто довгі дані відхиляються з тією ж відповіддю 401 до хешування | `test_login_does_not_hash_oversized_password` |
| 2 | Файл `instance/secret_key` створювався з правами 644 (читають інші користувачі системи) | Створення з правами 600 (`os.open`, `O_EXCL`) | `test_secret_key_file_is_private` |
| 3 | Немає індексів на зовнішніх ключах | `idx_subjects_user_id`, `idx_tasks_subject_id` у `schema.sql` | `test_foreign_key_columns_are_indexed` |
| 4 | Невикористаний імпорт | Прибрано | немає (косметика) |

Контрольний тест `test_login_with_normal_password_still_checks_hash` підтверджує, що звичайний вхід не зламано.
Результат: 100 тестів, усі проходять. На старому коді 3 з 4 нових тестів падали, контрольний проходив.

## Свідомо не змінювалося

- Дублювання JS-функцій: спільний файл `common.js` додав би ще одну залежність між сторінками, а код простий. Зафіксовано як борг.
- `error()` в `auth.py`: перенесення у окремий модуль `http.py` можливе, але зараз це лише косметика.
- Обмеження кількості спроб входу (rate limiting): відоме обмеження, у README.
- Індекси застосовуються тільки до нових баз: схема виконується при першому створенні файлу БД. Для вже існуючої бази потрібно видалити `instance/taskstudent.db` (дані зникнуть) або виконати два `CREATE INDEX` вручну.
- Сторінки `/` і `/subject/<id>` віддаються без перевірки входу; дані захищені на рівні API, сторінка без даних нічого не розкриває.
